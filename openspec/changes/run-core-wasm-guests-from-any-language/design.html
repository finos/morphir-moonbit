Context

See proposal.md, "Why", for the motivation. This section records only the current state that the design builds on. The research read this repository at fe9ca3dc and finos/morphir-gleam main at 737d1da7 (the guest, its host test tests/core_wasm.rs, its claims file and its bundle script), and ADR-0009 and the MEP draft in finos/morphir.

Goals and non-goals

Goals:

  • The core-wasm-process route runs any guest that conforms to morphir/mep-bytes-v1/v1-draft and MEP 0.2.0-draft.1, with no code for a particular language.
  • Assembly form pins and MoonBit guest behavior stay the same.
  • The new logic is pure MoonBit (source collection, claim selection, descriptor checks), so that the worker host can reuse it.

Non-goals:

  • Installing core-Wasm bundles from a repository, and joining installed extensions to invocation. These belong to acquire-extensions-from-repositories (morphir-ukvn.5.64.34) and morphir-ukvn.5.64.30.
  • Verifying signatures or GitHub artifact attestations. That is add-extension-trust.
  • Ion morphir-model for the Gleam guest. The guest does not offer it.
  • Incremental compilation, dependencies and exposed-module lists in the request.
  • The browser route and the native WASM worker. Those are in host-extensions-as-workers.
  • Changes to finos/morphir-gleam, finos/morphir-rust or finos/morphir.

One Gleam compile, from command to result

A user has a Gleam project in /work/shop. Its modules are src/shared/numbers.gleam, src/app/money.gleam and src/app/orders.gleam, and money and orders import shared/numbers. The user downloads the morphir-gleam 0.4.0 bundle, writes a module form pin over it, and runs this from the project directory:

export MORPHIR_EXTENSION_PIN=/work/gleam-pin.json
morphir extension compile src --package acme/shop --output model
morphir extension generate model/model-envelope.json --output generated

The diagram below shows what happens for the compile. There are two guest sessions. The first one only asks the guest what it is. The CLI uses that answer to build the second one, which does the work. Each session starts from verified copies, so a file that changes between the two sessions cannot change what runs.

In step 5 the claims say: language gleam with .gleam, multiDocument: true, the JSON tuple only, and target gleam. The walk of src finds the three files. The user gave no --model-format, so the CLI offers the Ion tuple first and the JSON tuple second. The first offered tuple that the guest claims is JSON, so the operation session agrees on JSON and the compile runs (SEL-2). With --model-format ion the command stops here with extension.tuple_unavailable, before the second session, and the message names the JSON tuple that the guest claims. For generate, step 5 selects the target gleam, because it is the only claimed target, and the guest returns one .gleam artifact for each module.

What replaces the MoonBit manifest checks

The MoonBit manifest does four jobs. A non-MoonBit guest needs three of them. The table maps each job to its replacement. The fourth job, MoonBit build provenance, has no truthful equivalent for another toolchain. The descriptor's gitCommit is reported as a claim instead.

Manifest job todayModule form replacementWho checks it
Bind the module bytes: artifact.size and artifact.sha256 Pin moduleSha256, the trust root, which must also equal the descriptor artifact's sha256. The descriptor is bound by descriptorSha256. CLI (descriptor); helper (both files, while it copies them)
Bind the execution profile: target wasm, encoding, profile ID and SHA-256 Descriptor artifact runtime: "core-wasm" and executionProfile, equal to the pin and to the host's constant. Every critical member must be one the host checks. CLI
Bind the module's interface: import names and kinds, exports A structural check of the module against the profile text: only the three byte imports with exact signatures, an exported handle: () -> i32, one defined unshared memory of at most 4,096 pages. Decisions

SEL-1. A describe-only probe session gives the claims

For compile and generate, the CLI first runs a describe-only session through the same helper and pin checks, and decodes the answer with Claims::from_describe. It then builds the operation session from those claims. The operation session still starts with describe, and its claims must equal the probe's (extension.claims_changed otherwise). This is the same pattern as the native route ("describes an immutable executable copy and closes that probe") and as probe and activation in the worker host.

Alternatives. (a) Take claims from the descriptor only, in one session. It does not work for assembly form pins, which have no descriptor, so the route would need two ways to choose a language. (b) An interactive session in the helper. It changes the helper protocol, which the worker host replaces anyway. (c) A required --language flag. It moves knowledge the guest already has to every user. Cost: one more Node start and one more module compile for each command. The task records the measured time for the 11 MB Gleam module.

SEL-2. The host offers every model tuple in preference order; --model-format requires one

Decided by Damian Reeves, 2026-10-30. The CLI advertises every model tuple that it supports for the operation, in its order of preference. The first tuple is the default. Today that is the Ion tuple (morphir-model, ion-binary), then the JSON tuple (morphir-ir, morphir-json). The order is the only signal for the default: there is no new wire field. The guest returns the intersection of its own support with the offer, in the host's order. The Rust SDK does this in NegotiatedModelTransport::select, and the MoonBit guest SDK does it in select_models (pkgs/morphir-moonbit/mep/model_transport.mbt). The session uses the first agreed tuple.

A guest that does not support the default but supports another offered tuple is a valid partner, not an error. Only an empty intersection is extension.tuple_unavailable. When the user gives --model-format, the CLI requires that format: it offers only that tuple, and a guest that does not claim it gives extension.tuple_unavailable with the claimed tuples in the message. generate offers the tuple of its input envelope first, and the CLI converts the model when the guest does not claim that tuple (SEL-4).

The CLI sends the operation request in the same pipeline as morphir.initialize, so the request must name its output tuple before the guest answers. The probe claims give that tuple: the CLI selects the first offered tuple that the guest claims for the operation, and an empty selection fails before the operation session. The operation session then requires the first agreed tuple to be that tuple, or the command fails with extension.agreement_mismatch, exit 1, and publishes nothing.

Decided by Damian Reeves, 2026-10-31. An agreement that differs from the probe claims has its own code. The first draft used extension.claims_changed, but that code means that the guest describes itself differently in the two sessions. In an agreement mismatch the claims can be the same in both sessions: the guest's negotiation does not follow its own claims or the host's order. A separate code tells the user to examine the guest's tuple negotiation, for example its SDK, and not its identity or capabilities. The name follows the <subject>_mismatch form of the existing worker host codes in pkgs/morphir-host/worker/outcome.mbt: extension.claims_mismatch, extension.digest_mismatch, extension.platform_mismatch and extension.abi_mismatch. The exit status is 1, as for extension.claims_changed, because the operation request is already in the pipeline when the agreement arrives. When the claims also differ, extension.claims_changed wins, because the describe answer comes before the agreement. The worker host uses the same code for an answer outside its offer or its order (finos/morphir-moonbit#283).

This changes a rule on main. extension_messages in apps/morphir/cli/extension.mbt says "Rich operations offer exactly the selected tuple: there is no silent codec fallback", and apps/morphir/docs/extension.md says "There is no fallback between them" and that initialization must "return the offered tuple". After this change, a compile without --model-format offers both tuples. This is not a silent fallback: the offer is explicit, the report records the agreed tuple, and the envelope names its own tuple. With --model-format there is still no fallback. Every command line that runs today runs the same way: the MoonBit guest claims Ion and gets Ion. Only a command that failed with extension.tuple_unavailable because the guest lacks the default now runs.

Evidence. finos/morphir-gleam#31 adds a host test that offers morphir-model with ion-binary first and the JSON tuple second; the morphir-gleam 0.4.0 guest agrees on JSON and compiles. Related. A matching text change to the MEP model transport section (spec/mep/model-transport.md) is open in finos/morphir#1115. This change does not edit finos/morphir.

Alternatives. (a) Keep Ion as the only offered default and fail early when the guest lacks it. This was the first draft of this design. It is too strict: it refuses a guest that supports a format the host also supports. (b) Add a wire field that marks the default. The offer order already says it, and a new field needs a protocol change. (c) Default to the only claimed tuple with a one-tuple offer. It gives the same result for the Gleam guest but hides the host's preference from the guest.

SEL-3. Language, extensions and target come only from claims

The selected LanguageClaim gives the language ID and the file extensions; --language selects one when the guest claims several. The only claimed backend target is the default target. The MoonBit checks extension.moonbit_source_required and the fixed default target moonbit go away. For the MoonBit guest, the claims give the same values, so its runs do not change. Its error code for a file with another extension changes to extension.source_required; the exit status stays 2.

SEL-4. The host library converts the model for generate when the guest does not claim the envelope's tuple

Rule decided by Damian Reeves, 2026-10-31; details (A to E below) decided by Damian Reeves, 2026-10-31. The envelope fixes the tuple of the model that the user gives, but the guest can claim a different generate tuple. If the host can convert the model to a tuple that the guest claims, it does the conversion for the guest and sends the converted model. The generate runs; this is not an error. Only when the guest claims no tuple that the host offers does the command exit 2 with extension.tuple_unavailable.

The offer follows SEL-2. The envelope's tuple comes first, because it needs no conversion. The other tuple that the host can convert to follows. When the guest claims more than one offered tuple, the host uses the first agreed tuple in its own order, so a guest that claims the envelope's tuple always gets the envelope unchanged. As for compile, the probe claims select the tuple before the operation session, because the request names its input tuple and carries the model. So the conversion runs before the operation session, and a refused conversion starts no operation session. The operation session must then agree on the selected tuple, or the command fails with extension.agreement_mismatch.

For example, a user generates from an Ion envelope with a guest that claims only morphir-ir with morphir-json for morphir.backend.generateModel. The host offers the Ion tuple, then the JSON tuple. The guest claims JSON, so the host converts the model to Morphir JSON. If the model has no metadata, provenance or non-profile annotations, the conversion loses nothing and the generate runs. If it has source provenance, the command stops with data.lossy_conversion and tells the user about --allow-model-loss. With that flag, the generate runs, the CLI writes a warning that provenance was dropped, and the output has a conversion record.

The decisions:

  1. A. Who converts. The host library, pkgs/morphir-host, converts with the codec registry of the engine (pkgs/morphir-engine/data/registry.mbt). That registry already has the morphir-json and Ion codecs and the loss check that bare morphir-json export uses. Every host front end, which is the CLI, the browser host and the worker host, calls the same conversion. No front end has its own converter.
  2. B. Directions. Both. morphir-ir with morphir-json to morphir-model with ion-binary is always lossless: a JSON model has no rich metadata to lose. morphir-model to morphir-ir with morphir-json is allowed only when it is lossless, unless the user gives --allow-model-loss. The flag applies to one generate command only; no configuration file or environment value sets it.
  3. C. Identity. The converted envelope keeps the modelId of the envelope that the user gave. Its revision is sha256: followed by the lowercase hexadecimal SHA-256 of the converted payload bytes, so the same input gives the same revision. The converted envelope holds no link to the original; the conversion record (E) holds it.
  4. D. Lossy conversion. Without the flag, a conversion that would drop data is refused with data.lossy_conversion, exit 2, before the operation session, with nothing published (committed: []). This is what the built-in morphir generate does today (apps/morphir/scripts/test-generation.ts). The message names the flag. It is not extension.tuple_unavailable: the guest claims a tuple that the host can send, and the refusal is about the user's model. With the flag, the command exits 0 when the generate succeeds, writes one warning to stderr for each kind of dropped data (metadata, provenance, annotations), and the JSON report has conversion: {from, to, dropped}. The report has the conversion object for every conversion; dropped is empty when nothing was lost.
  5. E. Retention. The host writes a conversion record, mep/conversion.json, next to the guest's artifacts and publishes it with them. It holds the original and the converted tuple, the original revision and payload SHA-256, the converted revision and payload SHA-256, and the dropped list (empty without the flag). The host does not copy the original model bytes; the payload SHA-256 identifies them. The guest's own retention sidecars (mep/source-model.ionb and mep/source-envelope.json for the MoonBit guest) stay as the guest returns them, so after a conversion they describe the converted envelope. The path mep/conversion.json is reserved for the host: if a guest returns an artifact at that path, the command fails with extension.result_invalid, exit 1, and publishes nothing.

A record after a lossy conversion with the flag can look like this. The member names are this design's choice; the implementation task fixes them in apps/morphir/docs/extension.md.

{
  "from": {
    "profile": "morphir-model", "codec": "ion-binary",
    "revision": "rev-2026-10-31", "payloadSha256": "<64 hex digits>"
  },
  "to": {
    "profile": "morphir-ir", "codec": "morphir-json",
    "revision": "sha256:<64 hex digits>", "payloadSha256": "<64 hex digits>"
  },
  "dropped": ["metadata", "provenance"]
}

The reserved-path refusal uses the existing code extension.result_invalid, exit 1, because the guest returns a result that the host cannot accept after the operation session ran. The conversion itself is not part of extension_generate_offer on main today: that function offers only the envelope's tuple, and says that the host does not convert a model (finos/morphir-moonbit#284). This change replaces that rule.

Alternatives. (a) Keep the rule that generate requires the envelope's tuple. It refuses a guest that the host can serve. (b) Tell the user to convert the model with another command first. It gives every user work that the host can do. (c) A converter in each front end. The three front ends would drift, and the loss check would exist in more than one place. (d) Copy the original model bytes into the output. It doubles the output size; the digest in the conversion record identifies the original.

SRC-1. Relative URIs from a source base, no sources.root

Each URI is the path relative to the source base: --source-base, or the current directory. A single file without --source-base keeps today's rule, so MoonBit requests are byte for byte the same.

Why not URIs relative to the named directory? For compile src, those URIs would be app/money.gleam. The Gleam 0.4.0 guest has no src segment to find, so it names the module money from the file name. The protocol says relative paths keep their nesting, so this is a guest deviation, not a host rule; but the host should not produce module names that depend on it. Why not synthetic absolute URIs with a root, as the guest's own host test does (file:///src/... with root file:///src/)? They would put invented absolute paths into diagnostics and source provenance, and the protocol root is meant to be a real location. Why not the real absolute paths with a real root? Host paths in the model break reproducibility across machines and break the existing rule that absolute host paths never enter provenance.

SRC-2. One portable source collector, with the Extism limits

A new pure function collects a tree into documents. It takes the claimed extensions, the language ID, the source base and the limits, and returns sorted documents or a typed refusal. Its file-system walk is an effect at the edge, with the same no-follow and bounded listing calls as extism_sources. The limits are the ones the Extism route already qualifies: 1,024 documents, 2 MiB of source in total, depth 32 and 16,384 entries. The core-Wasm limit of 1 MiB for one file stays. The 4 MiB framed request limit stays the final check, because JSON escaping can make the request larger than the sources. extism.mbt moves to the same collector with language python and .py, so the two routes cannot drift; its behavior and error codes stay the same.

Alternative: raise the request limit to the Node host's 16 MiB. The helper and the CLI both bound the request at 4 MiB today, and the Gleam real-world fixtures (13 files) fit well within it. A larger limit can come with the worker host, which owns the channel limits.

SRC-3. URI segments are percent-encoded, plain names are unchanged

The protocol says a frontend decodes path segments once and refuses encoded separators. The collector encodes each segment as an RFC 3986 path segment. Unreserved characters (letters, digits, -, ., _, ~) stay as they are, so ordinary paths and all existing MoonBit and Python requests are unchanged. Unsure: the Gleam guest's parsed_path must decode such segments correctly. The acceptance task includes one file name with a space to show it.

PIN-1. A module form inside the same pin contract

The artifact member gets a second form, chosen by form: "module". A member without form is the assembly form, so old pins stay valid. Exact field sets keep the forms apart. The module form follows the Extism pin (directory, descriptorSha256, extensionId, version), but names the descriptor file, because the Gleam bundle calls it morphir-gleam-0.4.0.release.json, not release.json. The module file name comes from the descriptor artifact whose digest equals moduleSha256.

Alternative: a new contract version such as 0.1.0-draft.2. It would mark the change more clearly, but it forces the MoonBit pins to be rewritten for no gain, and the worker host retires this contract for 0.2.0 anyway. See the open questions.

PIN-2. The descriptor is required for the module form, not a new manifest

The release descriptor is already the language-neutral record. A publisher writes it from a live describe, it names the runtime and the execution profile as critical members, and repository acquisition and the worker host both plan to read it. A new language-neutral manifest would be a third file with the same facts. The descriptor is required, because without it the route would have no record of the profile the module claims to implement, and no claims to compare. A module built from a source checkout gets a descriptor from the publisher's own bundle task (for Gleam, mise run rust:bundle).

INT-1. The CLI decodes the descriptor; the Node host checks the module

The CLI reads the descriptor with a 1 MiB bound, checks the digest, then decodes and checks it in pure MoonBit. The helper copies the descriptor and the module through no-follow descriptors and checks both digests again, so the bytes the CLI checked are the bytes that run. A new descriptor decoder goes into pkgs/morphir-host/worker, next to the claims decoder, so the worker host's pin 0.2.0 (which has an optional descriptor) can reuse it.

The structural check runs in the Node host, which is the place that loads the module. It extends the binary reader in wasm-memory.mts to read the type, import, function and export sections. It runs for both forms; for the assembly form it adds to the manifest checks and removes none. The host module closure keeps its twelve file names, so the pin's host.modules list does not change shape. node-mep-cli.mjs gets an explicit --module FILE form next to ARTIFACT_DIRECTORY. The host never guesses the form from a missing manifest.ion, because a deleted manifest must not silently turn off checks.

INT-2. Claims are compared, never trusted for authority

Three comparisons use Claims equality, which compares sorted sets: descriptor claims with the probe claims (extension.claims_mismatch, exit 2, before the operation), the probe with the operation session (extension.claims_changed, exit 1, after the guest ran), and pin identity with live identity. An agreement that does not start with the selected tuple is not a claims comparison: it is extension.agreement_mismatch (SEL-2). The decoder gets frontend.multiDocument, which Claims does not hold today; this changes Claims equality for the worker host too, which is correct, because a change in that claim changes which requests are valid.

ACC-1. Acceptance runs the real Gleam module, outside routine CI

scripts/portable-mep-gleam.mbtx (mise task test:portable-mep-gleam) takes the bundle from one of two explicit inputs: a downloaded release directory (MORPHIR_GLEAM_BUNDLE, checked against its .sha256 files and against MORPHIR_GLEAM_BUNDLE_SHA256 for the module), or a build from a pinned finos/morphir-gleam commit with MISE_ENV=rust mise run rust:wasm and mise run rust:bundle. It never chooses one silently. Like test:portable-mep-cli, it builds the embedding host and both CLIs, writes the pin, runs the real commands with an empty TMPDIR each, and writes evidence under .dev/portable-mep-gleam.

It compiles a fixture tree in apps/morphir/fixtures/gleam-tree/ (the three modules above and one file name with a space) and requires: success, the module names, and the payload equal to an expected file recorded for the pinned module digest. It generates from the envelope and requires one .gleam artifact for each module. It also requires that a compile with no --model-format agrees on the JSON tuple. Refusal cases: an explicit --model-format ion, a changed descriptor byte, a descriptor written again with other claims, a module digest mismatch, an unknown critical member, a link in the tree and 1,025 files. Routine CI keeps scripts/test-extension-provider.ts with a stand-in runtime and small crafted modules for the structural check.

Risks and trade-offs

RiskMitigation
Gleam 0.4.0 ignores relative nesting without a src segment, so compile . from inside src gives wrong module names (or DUPLICATE_MODULE). The documentation says to name the source directory from the project directory, or to use --source-base. The acceptance test pins this case. A guest fix belongs to finos/morphir-gleam.
Naming the project directory instead of src includes test/ and build/packages/*/src, and build/ can hold links. There are no hidden exclusions; the link refusal and the limits make the mistake visible. The documentation shows compile src. Exclusion options can come later.
Each call to the guest has a fixed 10-second deadline in the Node host. A large tree can exceed it. The Gleam guest test compiles all 13 real-world fixtures within that limit. The task records the measured time. The error is the existing extension.incomplete_session.
Without --model-format, the same command line gives an Ion envelope for one guest and a JSON envelope for another (SEL-2). The report records the agreed tuple, and generate reads the tuple from the envelope. A user or a script that needs one format gives --model-format, which has no fallback.
A guest that does not keep the host's order in its agreement makes the session use a tuple other than the host's preference. The CLI requires the first agreed tuple to be the tuple selected from the probe claims, so such a guest fails with extension.agreement_mismatch and publishes nothing.
The worker host change (host-extensions-as-workers) and the MEP text still describe a one-tuple offer until they are updated. The MEP text change is open in finos/morphir#1115. finos/morphir-moonbit#283 aligns the worker host's "Model tuple negotiation" requirement (see Relation to the worker host).
A converted model is not the model that the user gave, so generate output from the same envelope can depend on the guest (SEL-4). The conversion refuses to lose data unless the user gives --allow-model-loss for that command. The converted envelope has its own deterministic revision, the report has a conversion object, and mep/conversion.json links the output to the original revision and payload digest.
A guest that writes its own mep/conversion.json could hide or fake the host's record. The path is reserved for the host. A guest artifact at that path fails with extension.result_invalid and publishes nothing, with or without a conversion.
The probe session adds a Node start and a compile of an 11 MB module to each command. Measured in the acceptance task. The worker host removes the cost with one interactive session.
The descriptor schema 2.0.0-draft.2 belongs to the shared distribution library, and the core-wasm runtime name and executionProfile member are new there. Unknown critical members fail closed. The decoder checks only the members this route needs and names the schema version exactly.
No authenticated publisher: a pin over a tampered release is still "valid". The pin digests are the explicit trust root, as for every pin today. Attestation verification is add-extension-trust.
The structural check lives in TypeScript, and the worker host will write it again in MoonBit. It is small, and both must pass the same crafted modules. Group 5 of the worker host can reuse the test modules.

Migration plan

Toolchain. The MoonBit toolchain moves from 0.10.17 to 0.10.18, with moonbitlang/async 0.22.7, on branch DamianReeves/async-0-22-7. The implementation of this change follows that toolchain and adds no 0.10.17 pins.

No migration is needed for existing users. Assembly form pins and MoonBit guest requests do not change. Pins must be written again after the embedding host is rebuilt, as today, because the module digests change. A compile without --model-format now offers both tuples; with the MoonBit guest it still agrees on Ion. A generate whose envelope tuple the guest does not claim now converts the model (SEL-4) instead of failing with extension.tuple_unavailable. A conversion that would lose data fails with data.lossy_conversion, exit 2, unless the user gives --allow-model-loss. To roll back, revert the change; module form pins are then refused with extension.invalid_pin, which is the current behavior.

Open questions

The design makes a choice for each open question below. The maintainer can change these choices without a change to the task breakdown.

  1. Default tuple (SEL-2). Answered. Damian Reeves decided on 2026-10-30: the host offers every supported tuple in preference order, the first is the default, and the session uses the first agreed tuple. An explicit --model-format offers only that tuple. Only an empty intersection is an error.
  2. Agreement code (SEL-2). Answered. Damian Reeves decided on 2026-10-31 that an agreement that differs from the probe claims has a new code, extension.agreement_mismatch, not extension.claims_changed.
  3. Conversion for generate (SEL-4). Answered. Damian Reeves decided on 2026-10-31 that the host converts the model when the guest does not claim the envelope's tuple, and then decided the details: the host library converts with the engine codec registry for every front end; both directions, JSON to Ion always lossless, Ion to JSON only when lossless unless --allow-model-loss; the converted model keeps its modelId and gets a sha256: revision of its payload; a lossy conversion without the flag is data.lossy_conversion, exit 2; the host writes mep/conversion.json and reserves that path; and with several convertible agreed tuples the host uses the first in its own order. See SEL-4. Two choices of this design remain for review: the member names of the conversion record, and extension.result_invalid (exit 1) for a guest artifact at the reserved path.
  4. Pin contract version (PIN-1). Keep 0.1.0-draft.1 with a form member, or bump it?
  5. Descriptor required (PIN-2). Should a bare module with no descriptor be runnable for local development, for example behind an explicit flag? The design says no.
  6. Gleam relative nesting. Should finos/morphir-gleam be asked to keep the nesting of relative URIs with no src segment, as the protocol text says? This change does not depend on it.
  7. Release availability. The release extension/gleam/v0.4.0 did not exist on 2026-10-30. Until it exists, acceptance builds from a pinned finos/morphir-gleam commit; the expected payload file must be recorded again for the released digest.
  8. Percent-encoding (SRC-3). It is not yet shown that the Gleam guest decodes encoded segments. If it does not, the collector can refuse such names instead.
  9. Overlap with the worker host. Which change owns the archived source-selection requirement (see Relation to the worker host)?
  10. Scope after the worker host landed. Since this design was written, main runs extension commands on the worker host (finos/morphir-moonbit#278, #279, #280, #284). The CLI now probes the guest, takes the language and the multi-document permission from the claims, runs WASM guests with pin contract 0.2.0, and refuses the options of the retired helper routes. The tasks of groups 1 and 3 that name the Node helper, node-mep-cli and the 0.1.0-draft.1 module form pin may already be done on main or no longer apply. Should this change be cut down to the source-tree collector (group 2), the generate conversion (SEL-4) and the Gleam acceptance (group 4)? This update records the SEL-4 decisions and does not change the scope.
